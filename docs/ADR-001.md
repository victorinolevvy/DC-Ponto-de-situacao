# ADR-001 – Stack e Decisões de Arquitectura

## Contexto

O departamento necessita de um MVP para recolher relatórios quinzenais dos projectos de electrificação rural, disponibilizando dashboards e exportações. A iteração inicial foca no backend, autenticação e CRUDs base.

## Decisão

Adoptar **NestJS 11** com **Prisma** sobre **PostgreSQL** para o backend, estruturado por módulos (Auth, Localização, Projetos). Utilizar JWT para autenticação simples com perfis (`Gestor`, `Director`, `Admin`). Utilizar `docker-compose` para provisionar a base de dados local. Respostas da API seguem o envelope `{ success, data, error }`.

## Justificativa

- **NestJS** fornece arquitectura opinativa (módulos, injeção de dependências) facilitando a expansão incremental (contratos, marcos, relatórios) e integração futura com websockets/exportações.
- **Prisma ORM** agiliza a modelação declarativa e gera clientes typesafe, acelerando queries complexas para dashboards e histórico.
- **PostgreSQL** alinha-se com requisitos futuros (funções geográficas, analytics) e é facilmente hospedado em serviços como Render/Neon.
- **JWT** simplifica autenticação no MVP mantendo possibilidade de evolução para Azure AD.
- **docker-compose** padroniza o setup local e CI.
- Envelope de resposta consistente simplifica o consumo pelo frontend e exportações.

## Consequências

- Necessidade de gerir migrações Prisma a cada iteração.
- Testes devem mockar `PrismaService` ou usar bases transitórias.
- Futuras integrações (ex.: Azure AD) exigirão adaptação do módulo de Auth, mas isolado por módulo.
- Frontend deverá consumir endpoints versionados com prefixo `/api` e lidar com `accessToken` JWT.

### Actualização I3 – Semáforo provisório

- O endpoint `/projetos/:id/resumo` calcula um semáforo provisório com base nas datas previstas de fim dos contratos: vermelho quando há prazos vencidos, amarelo para prazos dentro de 30 dias e verde caso contrário. Também apresenta próximas datas-chave a partir dos marcos futuros.

### Actualização I4 – Relatórios quinzenais & semáforo definitivo

- Foram introduzidos endpoints dedicados a relatórios quinzenais (`POST/GET /projetos/:id/relatorios`, `GET /relatorios/:id`, `PATCH /relatorios/:id`, `GET /projetos/:id/evolucao`, `GET /projetos/:id/ultima-quinzena`) com paginação, filtros e histórico preservado.
- O cálculo do semáforo tornou-se definitivo: vermelho quando há atraso explícito, derrapagem física >10pp (a nível do projeto ou de qualquer contrato) ou texto de risco com termos críticos; amarelo quando há riscos activos, derrapagem entre 5-10pp (projeto/contrato) ou contratos a ≤15 dias da data prevista; verde caso contrário. O resumo devolve também os motivos que originaram o estado para transparência.
- Foi definida a variável `RELATORIOS_TOLERANCIA_FUTURO_DIAS` (padrão 3) para validar que `dataRef` não ultrapassa a tolerância e foram adicionados limites específicos de rate limiting nos endpoints sensíveis.

### Actualização I5 – Dashboard consolidado & exportações

- Criado módulo dedicado `/dashboard/overview` que agrega KPIs, lista consolidada de projectos e reaproveita a lógica de semáforo definitiva partilhada entre Projectos e Dashboard.
- A lista suporta filtros (`provinciaId`, `tipoProjeto`, `estado`), ordenação (`sortBy`, `sortOrder`) e paginação (`page`, `pageSize`), devolvendo ainda os motivos do semáforo para cada projecto.
- Foram adicionadas exportações (`format=xlsx|pdf`) geradas no backend (ExcelJS/PDFKit) com os mesmos filtros aplicados, garantindo consistência entre a tabela visualizada e o ficheiro entregue.

### Actualização I6 – Operacionalização & UX

- Introduzidos scripts raiz (`dev:stack`, `dev:demo`) para acelerar o arranque local com Docker (Postgres) ou com fallback SQLite automático quando `DATABASE_URL` não é fornecida.
- As exportações Excel/PDF passaram a incluir cabeçalhos com filtros aplicados, data/hora de geração, formatação monetária/percentual e rodapés com paginação.
- A API `/dashboard/overview` passou a expor `riscoCompleto` e a truncar `riscoCurto` com reticências, facilitando tooltips no frontend.
- O frontend recebeu badges de semáforo com tooltip de motivos, tabela com botão de detalhe, modal com resumo/contratos/datas-chave e interacções de KPI que aplicam filtros automaticamente.
- Adicionado workflow GitHub Actions que executa lint + testes, constrói FE/BE e gera screenshots (home e detalhe) com Playwright para validação visual contínua.
